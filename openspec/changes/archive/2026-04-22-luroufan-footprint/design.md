## Context

目前 bot 的照片辨識流程在辨識完成後直接給出結果，沒有任何記錄機制。用戶缺乏持續回訪的動機，平均互動 2-4 次後就不再使用。

足跡打卡功能讓用戶每次吃魯肉飯都能記錄，累積打卡數同時解鎖稱號，形成長期使用習慣。

打卡範圍涵蓋兩個資料庫：`store_notes`（24 家）與 `hidden_gems`（74 家），共 96 家（扣除 2 組重複店家）。

## Goals / Non-Goals

**Goals:**
- 照片辨識後提供打卡確認入口
- 辨識失敗/平手時以位置補救，讓用戶仍能完成打卡
- 打卡記錄存入 Firestore，持久化
- 用戶可查詢自己的足跡清單

**Non-Goals:**
- 不實作稱號系統（獨立 change）
- 不實作社群感功能（獨立 change）
- 不驗證用戶是否真的去過該店
- 不支援刪除或修改打卡記錄

## Decisions

### 打卡確認流程

照片辨識成功後，在現有回應下方加 Quick Reply「就是這家 ✅」。用戶點選後才記錄，不自動打卡。

**理由**：辨識有誤判率，不能假設辨識結果即為用戶實際到訪的店。

### 辨識失敗/平手的補救路徑

辨識失敗或平手時，在大叔回應下方加 Quick Reply「打卡這碗 📍」，用戶點選後系統請求分享位置，列出兩個資料庫合併的附近店家（半徑 500 公尺），讓用戶選一家。

**理由**：位置是辨識失敗時唯一可靠的確認方式，500 公尺足以覆蓋用戶吃飯的當下位置。

### Firestore 資料結構

```
user_footprint/<user_id>/records/<record_id>
  store_name: string
  db: "store_notes" | "hidden_gems"
  checked_in_at: timestamp
```

每次打卡新增一筆 record，同一家店可重複打卡（記錄多次造訪），但足跡查詢以「去過幾家不同的店」計算。

**理由**：保留完整造訪歷史，比只記錄「是否去過」更有資料價值。

### 足跡查詢顯示

用戶輸入「足跡」，以 Flex Message 顯示：
- 打卡總家數（不重複）/ 96 家
- 最近一次打卡店名與日期
- 吃過的店家清單（最多顯示 10 筆，依時間倒序）

### 寫入非同步執行

Firestore 寫入在 background thread 執行，不阻塞 webhook 回應。

**理由**：與 `taste-preference-persistence` 的做法保持一致。

## Risks / Trade-offs

- **辨識誤判仍可打卡**：用戶確認的是自己的選擇，bot 不攔截 → 可接受，責任在用戶
- **附近無店可選**：位置補救找不到 500 公尺內的店時，顯示提示，本次打卡略過 → 可接受
- **重複打卡**：同一家店打卡多次，足跡查詢去重顯示 → 不影響體驗
